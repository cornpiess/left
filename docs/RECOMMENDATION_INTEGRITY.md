# 推荐流重复与覆盖完整性修复

审查基线：`cornpiess/left` main `6408eb4a5fb58faa86d2031160994aa618eecbcb`。

## 业务规则

同一个 assetId 在主推荐的已承诺卡片、候选、溢出、回流中只能有一个归属。成功显示且稳定激活后写入 SQLite 已读历史；预加载不记已读。已读不作为新推荐，耗尽进入完成态。主动回看、恢复当前节点、当天上下文浏览允许显示已有历史。

默认探索与大文件优先共享同一条候选、去重、分组、分页和已读链路，只改变局部候选排序。保留现有节奏，不引入图像分析、全库文件大小扫描或新的推荐模型。

## 确认的问题与修复

| 问题 | 原因 | 修复 |
| --- | --- | --- |
| 同一照片占据两张主流卡片 | 原生连拍展开直接替换成员，仅移除候选重复，没有排除其他已承诺卡片 | 展开通过会话统一认领 ID；已承诺归属优先，同时清理候选、溢出和回流中的重叠 |
| 旧照片在裁剪后重新出现在前方 | Home 在第 80 条附近裁剪界面历史，但会话保留完整旧前缀；补页从会话重新投影全部历史，当前数组下标却不变 | 由会话裁剪，保留近期 40 条历史；会话与界面使用同一窗口，锚点和曝光进度不变 |
| 部分连拍成员永远不出现 | 已承诺组拒收晚到成员；160 项上限直接截断成员；从原生第一页展开时覆盖落在后续页的抽样种子 | 晚到和超限成员保留原生身份、进入单卡调度；展开保留已抽到的种子与邻域 |
| 筛选异常后漏过一页 | 分页游标在分组、SQLite 资格查询和排序成功前已推进 | 整页成功后才提交游标、边界组和扫描进度；失败重试原页 |
| 同日浏览后再次出现已看照片 | 同日浏览可看过主流预取的未来卡片，而旧卡片仍留在已承诺窗口 | 同日已读提交后移除未来重复；分页也复查未来卡片，保留当前节点与回看历史 |
| 超过十分钟的视频优先级反而下降 | 将大于 600 的 duration 猜成毫秒，但候选来自 legacy API，单位始终为秒 | 按来源的秒单位计算；规范化媒体类型，保持估算分数随时长单调增长 |
| 空间优先的普通照片按原采样顺序排列 | 两个模式分别调用排序，空间优先缺少随机底序 | 共用排序入口，先打乱，再按空间估算优先级稳定排序 |

前三项复现分别包含生产 media/native 适配链路、会话窗口与实际数据流。旧代码中的原生扩展重复、晚到成员丢弃、筛选失败跳页均由新增回归测试直接复现。用户描述的“20–30 张”不能仅凭代码确定为固定触发间隔；窗口裁剪条件为约 80 条，连拍与同日路径不依赖这个阈值。

旧快照恢复时会去除主流各队列已有的重叠 ID，不清空已读、待删或额度。

## 排序能力边界

- 默认探索是首批跨年代分层抽样，后续 PhotoKit 按时间分页、页内随机，不是全库等概率的随机排列。这个覆盖与新鲜度限制不等于重复分发；本次保留现有抽样结构。
- 大文件优先在已获取的局部候选中排序。优先用已知大小，否则按视频秒数、像素、Live 和组成员估算；不宣称按全库真实字节严格降序。
- 保留 2 张开场单卡、组间 3–5 张单卡；已读依赖 SQLite，4096 项热缓存不承担完整历史的正确性。

## 回归与发布验证

`tests/recommendation-integrity.test.mjs` 执行真实生产 media 管线及 SQLite 适配，覆盖：重复归属、旧快照、原生展开与成员上限、分页失败、历史裁剪、同日已读，以及两种模式各 5000 张连续遍历。遍历越过 4096 项热缓存上限，在 4200 张后重启，检查零重复、零遗漏、能到达完成态。原生图库另覆盖 6 组、共 1080 个成员。

已有回归继续覆盖待删事务、额度、350 帧原生续页、重启与异步重置隔离。

本地结果：`npm test` 共 296 项通过（原有 284 项、新增 12 项），不可变绑定检查通过，`expo export --platform ios` 成功生成 Hermes bundle。这些验证不替代 iOS 二进制构建和真机手势回归；发布前重点实测：持续刷过 100 张、连拍跳出后继续刷、同日浏览返回、重启、切换两种模式、有限权限与 iCloud。
